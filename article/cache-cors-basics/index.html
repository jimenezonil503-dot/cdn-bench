CDN 缓存与 CORS 配置：从响应头到上线验收，排查内容不更新和跨域失败

接入 CDN 后内容不更新、接口跨域失败或登录状态异常，应该先查什么？按缓存层、Cache-Control、缓存键、CORS 和 OPTIONS 拆解上线验收。

页面能打开，为什么接口还是报错

把资源接到 CDN 后，常见的麻烦不一定是速度，而是行为改变了：浏览器地址栏能打开文件，页面脚本却读不到；后台已经发布新内容，用户仍看到旧版本；匿名访问正常，登录后偶尔拿到不该出现的结果。这些现象分别涉及跨域权限、缓存更新和响应隔离，不能用“刷新一下 CDN”统一解决。

可以先记住一个排查顺序：确认实际请求和响应，识别是哪一层缓存，再检查跨域许可与业务身份。响应状态、Content-Type、Cache-Control、Age、Vary 和相关平台的命中信息，都比页面上的笼统报错更接近事实。不过，单个头字段也不能包办判断，仍需结合 CDN 规则、浏览器行为和源站日志。 本文围绕一个假设的业务组合展开：公开文章页、带内容指纹的静态文件，以及登录后的接口。所有配置取舍都应回到资源特性。需要先确定接入服务的读者，可以从CDN 选型指南开始；本文则关注接入以后怎样保证内容正确、更新可控和问题可复查。

先分清浏览器缓存、边缘缓存与源站

浏览器缓存为本地访问保存内容，CDN 边缘缓存可能为多个访问者复用内容，源站则产生或保存原始响应。清除 CDN 缓存，只影响相应边缘层，通常不能让已经保存内容的浏览器立即忘掉文件。反过来，在自己的浏览器里清缓存，也不代表其他用户或边缘节点发生了同样的变化。

这一区别直接影响发布策略。若一个脚本文件长期缓存，又不断覆盖同一个 URL，用户可能在一段时间内继续得到旧内容。对于版本化资源，更稳妥的设计通常是内容变化就更换 URL，页面引用新版本，同时保留旧资源一段时间。这样旧页面仍能找到对应文件，而不必要求所有缓存同时刷新。 公开页面和用户接口不能照搬这套长期缓存思路。文章改错可能允许短暂延迟，库存、交易状态和用户资料却有不同的正确性要求。上线前写清每类资源允许多久不更新，再决定 TTL、验证和失效策略；不能因为默认设置方便，就让所有内容共享一组参数。

no-cache 与 no-store 不只是名字相近

MDN 的 Cache-Control 文档区分了多个响应指令。no-cache 的核心含义是复用前需要验证，并不等于完全不能存储；no-store 则要求缓存不要存储该次响应。把二者当成同义词，容易让排查朝错误方向走。还要区分请求指令和响应指令，不能看到请求写着某个值，就推断每一层已经按同样方式处理。

private 表达的是响应不应存入共享缓存，而不是一份身份验证机制。它不会代替登录校验，也不能阻止拿到响应的用户自行保存内容。public 则允许共享缓存存储符合条件的响应，不能因为想提高命中率就给个人化页面加上它。缓存许可和业务访问权限，是两件必须分别设计的事。 max-age 表示新鲜度时间，s-maxage 面向共享缓存，适用范围有所区别。即便源站已经给出合理指令，CDN 上的自定义规则仍可能改变行为。排查时应把源站响应和边缘实际返回进行对比，并核对规则优先级。标准文档说明指令语义，服务商文档说明平台具体怎样实现，两种证据缺一不可。

缓存键写错，内容就可能被错误地复用

缓存键可以理解为缓存系统识别一份响应的依据。路径相同，但语言、图片尺寸、查询参数或身份条件不同，响应可能不同；这些差异如果没有被正确识别，就有错误复用的风险。反过来，把每个随机参数都纳入键，又可能使原本相同的内容无法共享，造成大量重复对象与回源。

CloudFront 缓存策略文档说明了请求头、Cookie 和查询参数如何参与缓存键。设计时可以从业务逻辑反推：哪些输入确实改变响应，哪些只是统计来源，哪些带有身份或签名信息。不能为了提高命中率就一概忽略查询参数，也不能为了“保险”把所有信息都加进去。 用图片处理接口举例：宽度参数改变输出尺寸，通常需要区分；一个仅用于访问分析的参数可能不改变内容，但是否可以忽略仍需确认应用行为。带访问签名的请求还涉及授权和有效期，必须检查命中缓存时访问控制是否仍然成立。高命中率如果来自错误地绕开业务条件，就不是优化结果。

登录态、Cookie 和 Authorization 要先画边界

用户相关接口的默认原则应是谨慎处理共享缓存。个人资料、订单、余额和后台操作，不适合仅凭路径相同就复用响应。测试时需要至少两个不同身份的账号和一个匿名访问者，确认每次得到的是正确内容；仅用一个账号反复刷新，很容易漏掉隔离问题。

响应带 Set-Cookie 时，平台的默认缓存处理也可能不同。Cloudflare 默认缓存行为列出了相关条件，但实际结果仍与配置有关。不要根据某个平台的默认设置，推断所有产品或自己新增的规则都能提供相同保护。规则变更需要重新跑业务用例。 Authorization 等请求信息同样不能仅靠名字判断。哪些请求转发到源站、哪些字段参与缓存键、命中缓存前是否执行权限判断，都应说清楚。对确实公开且与用户无关的响应，可以单独建立安全策略；对不确定的接口，先保持不共享缓存，再通过明确的业务审查逐步放开。

CORS 控制脚本读取，不负责保护你的业务接口

MDN 的 CORS 指南解释了浏览器怎样根据响应中的许可决定是否将跨域响应交给脚本。这里的跨域由协议、主机名和端口共同决定。两个地址看起来属于同一个品牌，也可能是不同来源；而命令行客户端通常不会按浏览器的相同方式执行这项限制。

因此，“浏览器报跨域错”不能直接解释成请求没有到服务器。某些请求可能已经发送并被处理，只是响应没有对脚本开放。身份认证、授权和防跨站请求伪造等机制仍需要独立设计。把允许来源写得很窄，不等于接口对所有其他调用者都无法访问。 对于公开、无需凭据的静态资源，可以按产品用途选择允许范围；对于携带凭据的请求，需要明确允许的来源，并满足相应凭据配置。不要照抄一个通配符就以为覆盖了所有场景。实际使用是否带 Cookie、是否需要额外请求头、请求方法是什么，都应纳入测试。

带凭据的跨域请求，为什么不能随意用星号

在带凭据的跨域读取场景中，Access-Control-Allow-Origin 不能使用通配符代替具体允许来源。服务器需要按可信名单判断请求来源，再返回符合规则的许可。同时，浏览器端的凭据模式、Cookie 自身的属性与其他安全限制也会影响结果。即使一处响应头正确，整条请求链仍可能没有满足条件。

不要把请求中的 Origin 原样反射回去，便宣称完成了安全配置。首先要判断它是否属于允许的来源，其次要考虑缺失或不匹配时怎样处理。对于包含个人数据的接口，跨域许可的变更应和访问权限一起审查，而不是由前端为了消除报错临时放开。 更容易复查的做法是准备三组请求：允许来源、未允许来源和正常同源调用。验证响应头和页面行为是否符合预期，再观察边缘命中后是否仍然正确。仅看到一次成功，不能证明策略不会对其他来源错误放行，也不能证明缓存没有复用上一次的许可。

动态返回允许来源时，要同时检查缓存变体

如果服务器依据 Origin 返回不同的 Access-Control-Allow-Origin，就需要考虑缓存如何区分这些响应。MDN 的 CORS 文档给出了 Vary: Origin 的相关说明。但把 Vary 写进响应并不意味着所有 CDN 配置都会自动按你想象的方式存储变体，仍应核对平台支持与实际缓存键。

一个典型排查思路是：先从允许来源甲请求，再从允许来源乙请求，观察命中缓存后许可字段是否与来源匹配；随后测试未允许来源。如果响应体本身还随身份或其他条件改变，问题会更复杂，不应只靠 Origin 区分。跨域权限正确与内容隔离正确，需要分别验证。 同样要检查响应错误时的头信息。成功响应带有跨域许可，错误响应没有，前端就可能只能看到笼统网络错误，无法读取业务错误码。团队应决定哪些错误响应可以公开，以及如何在边缘和源站一致地返回；不能为了调试方便把所有敏感错误内容暴露出来。

OPTIONS 预检不要和正文请求混成一个指标

某些跨域请求会先进行 OPTIONS 预检，浏览器确认允许的方法和请求头后，再发送实际请求。是否需要预检取决于请求条件，而不是简单地由 GET 或 POST 两个字决定。预检失败时，实际请求可能根本没有按预期发送；这与已经返回正文但脚本无法读取，是不同的排查路径。

检查网关和防护规则是否正确处理 OPTIONS，确认重定向、认证要求或统一拦截是否影响它。预检响应与实际响应各自需要什么许可，也要分别核对。对于返回缓存结果的边缘节点，仍然要确保相关许可与当前请求相符。不要只测试一个最简单的无凭据请求，就认为复杂业务已经覆盖。 预检结果的缓存也有独立机制，不能与文件内容的 CDN TTL 混为一谈。浏览器行为和限制需要参照对应文档与实际环境。排查期间修改了配置而结果没有立刻变化时，应明确是哪一层状态仍在生效，再选择适当的验证方式，避免反复调整多个地方后失去因果关系。

清缓存以后还看到旧内容，按这条顺序检查

先确认部署是否真的更新：源站对应路径返回的是哪个版本，构建产物与页面引用是否匹配。随后检查边缘层是否命中、刷新任务是否针对正确域名和路径，以及查询参数或不同内容变体有没有漏掉。接着看浏览器是否仍在复用本地内容，最后检查页面中是否有应用级缓存或其他中间层。

不要一次性清空所有缓存作为默认操作。大范围失效可能增加回源压力，也会让现象暂时消失而原因仍然存在。能够定位到一个版本、路径或资源集合时，就先使用有范围的刷新，并观察源站负载。对于重要发布，提前安排回滚和旧资源保留，比出问题后临时寻找文件更稳妥。 还要确认“旧内容”是否其实来自不同数据源。例如页面引用了旧接口地址，或者部分用户仍使用旧版客户端，单独刷新 CDN 不会修改它们的请求。版本标识、响应日志和发布时间可以帮助关联问题，不必依赖用户描述中的“好像还是昨天那版”。

接入高防或境外线路，也不能省掉这份配置验收

更换为高防CDN后，除了交付与缓存，还应关注规则是否影响接口、预检和合法机器调用。若某个错误响应实际是防护页面，需要结合事件日志定位，不能简单地补一个跨域头就算修好。防护产品的公开资料是功能说明，业务是否兼容仍然需要按真实流程验证。

采用免备案CDN等接入方案时，域名与线路条件也不会改变 HTTP 缓存和浏览器权限这些基本问题。目标地区、回源方式与缓存策略都要重新核对。不同服务商的控制台术语可能不同，迁移时应逐项映射行为，不要只按开关名称一一照搬。 比较不同平台可以参考CDN5、Cloudflare 与接入方案分析。其中最重要的思路同样适用于配置：保留待确认项，记录实际响应，不把某家官方介绍或一张控制台截图当作完整验收。

上线前最后一轮，应由业务请求来验收

准备匿名、登录和不同权限身份，分别访问公开页面、静态文件和关键接口；让允许与未允许的跨域来源各执行一次；更新一份资源，确认新旧版本的处理符合计划；模拟一个可撤销的错误，观察状态、日志和恢复。测试都在自己有权操作的范围内进行，并记录具体请求与时间。

随后验证监控是否能发现内容类型错误、异常状态、命中率变化和回源突增。监控图表不必很多，但需要让值班人员知道何时采取什么动作。对外发布前保存最终配置和回滚入口，避免测试时临时增加的许可或放行规则留在生产环境。 如果还想用浏览器观察读取表现，可以使用实测工具并结合测速指标解释。不过，速度只能在内容和权限都正确时讨论。一次正确的缓存命中，应同时满足对象正确、用户正确、许可正确和更新策略正确；少了任何一项，数字再快也不能算完成优化。
