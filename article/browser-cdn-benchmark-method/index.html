CDN 测速怎么测才有用：响应时间、下载速度与失败率的正确读法

先说结果：浏览器测速有用，但它回答的是一个局部问题

打开测速页，看到某个节点用了二百多毫秒，另一个用了四百多毫秒，很容易就想排出名次。问题是，这两个数字可能同时受到文件、压缩、缓存、连接复用和本地网络影响。浏览器测速真正能够回答的是：在这个时间、这个设备和网络条件下，读取这份资源的表现如何。把条件写在结果旁，它才是一条可以复查的证据。

这并不意味着浏览器数据没有价值。它可以帮助发现某个访问地明显超时、某份资源不支持跨域读取，或者同样内容经过不同交付路径时出现稳定差异。但它不能单凭几次请求证明全球性能，更不能把文件下载速度当作 DDoS 防护测试。测速前先写下要回答的问题，往往能省掉大量无意义的重复点击。 本文按本站工具的实际实现解释指标，再给出可执行的对比流程。涉及 API 行为的依据来自 MDN 等官方技术资料；文中的数字例子用于说明计算方法，不是对任一服务商的测评。完整指标范围可与本站测量说明一起阅读。

从发起请求到读完文件，中间至少有两个重要时间点

第一个时间点是收到响应头，第二个时间点是响应体全部读完。MDN 的 Fetch 使用说明解释，fetch 返回的 Promise 获得响应时，响应体不一定已经全部到达。若只记录请求发出到 Promise 完成的时间，你看到的就不是整个文件的下载时间。

本站的响应耗时，从发起调用前计时，到拿到响应对象为止。它可能包含浏览器调度、连接建立或复用、网络往返、服务器处理等影响，并没有单独拆出每个阶段。因此，它适合在受控条件下比较等待响应的表现，不应直接命名为 Ping，也不能被解释成单纯的源站处理时间。 完整请求耗时则持续到响应体读取完毕。假如响应很快开始，但文件传输缓慢，两项指标会拉开距离；假如等待很久后迅速返回小文件，则主要时间可能消耗在前一段。两项一起看，比单独挑出一个好看的指标更有助于判断下一步该检查连接、缓存还是源站。

“有效速率”不是你家宽带的测速结果

本站有效速率的计算方式是：实际读取的响应体字节数乘以八，再除以完整请求耗时，换算成 Mbps。它包含等待响应的时间，因此一个很小的文件即使传输阶段很快，也可能得到不高的数字。反过来，压缩或缓存等因素又可能让结果与真实线路承载的数据量产生明显差别。

用一个纯演示的例子：一百万字节在一秒内读完，按这个口径约为 8 Mbps。如果相同内容被压缩后只传输其中一部分，而页面读取的是解码后的响应体，计算出来的数值仍以读取字节数为基础。它描述的是该次任务的有效读取效率，不等于线路额定带宽，也不是账单上的传输字节数。 PerformanceResourceTiming 文档区分了传输大小、编码后的响应体大小和解码后的响应体大小。若需要解释压缩差异，应结合浏览器网络面板和适当的时序数据，而不是将这些字段混用。报告必须注明字节口径，否则同样写着 Mbps 的两张图也可能无法比较。

CORS 失败为什么经常被误认为 CDN 故障

浏览器跨域读取资源，会受到 CORS 规则限制。地址在新标签页里能打开，不代表另一个网站里的脚本就能读取它。服务器可能已经返回内容，浏览器却因为响应没有允许当前来源而阻止脚本访问；测速工具因此无法得到可用结果。这个失败首先表示该种读取方式没有完成，不直接证明服务商节点宕机。

MDN 的 CORS 说明指出，出于安全考虑，脚本得到的错误信息通常不足以说明全部细节。应查看开发者工具中的网络和控制台信息，再对照响应头与服务端日志。域名解析、证书、超时和跨域配置，都可能需要不同的排查路径，不能仅凭一个统一错误提示下结论。 本站请求不携带身份凭据，适合公开且允许读取的测试文件。不要拿登录接口、带私人令牌的链接或包含个人信息的文件当测试对象。需要调整跨域配置时，可以参照缓存与 CORS 配置指南，确认允许来源与资源敏感程度相匹配。

CORS 与跨域性能时序，还是两回事

即使页面已经能读取响应，也不意味着所有细分网络时序都向页面开放。PerformanceResourceTiming 对跨域资源的一些字段有限制，官方文档说明可以通过 Timing-Allow-Origin 控制相关信息的开放。它与允许读取响应的 Access-Control-Allow-Origin 承担不同职责，不能互相替代。

因此，一个测试页能下载文件，却无法准确列出 DNS、连接或 TLS 的分段耗时，并不矛盾。若报告声称测得了某个阶段，应说明数据来自哪里，以及目标资源是否满足采集条件。缺失字段不要补成零延迟，也不要把浏览器隐藏的数据当作服务端没有发生该阶段的证据。 对一般选型来说，先稳定比较完整读取和成功率，通常已经能发现明显问题。只有在需要定位细分阶段时，再增加时序采集和目标资源配置。不要为了让报告显得专业，填入工具没有实际采集的指标。可解释的少量数据，比字段很多却无法复查的报表更有用。

同一个文件名，也可能不是同一个测试对象

公平比较需要固定内容版本、对象大小和返回类型。一个地址返回压缩脚本，另一个返回未压缩文件，还有一个地址实际跳到了 HTML 提示页，把三者放进速度榜显然不合适。即使路径都以同样的后缀结尾，也应检查实际响应，必要时校验文件内容或摘要。

本站默认示例使用公共库资源，目的是方便观察当前浏览器的读取行为。公共库分发与自有域名接入的 CDN 服务，并不是相同的采购对象。若要比较候选服务，应把自己有权使用的相同文件部署到各家测试域名，并配置一致的响应与缓存条件。不要用不同厂商官网首页充当同一性能样本。 对象大小也应贴近任务。小文件更容易受到连接和等待时间影响，大文件能覆盖更多传输阶段，却会增加测试流量。本站限制单次读取大小并拒绝 HTML 响应，是为了控制资源使用和明显的错误对象。测试量应事先估算，移动网络下尤其要注意，不要用不断增加轮次代替合理设计。

冷缓存、热缓存和随机参数要分别理解

本站会加入随机查询参数，并使用不读取浏览器 HTTP 缓存的请求选项，以减少部分本地缓存干扰。但这不等于保证每次都绕过 CDN 缓存。边缘如何处理查询参数，取决于实际缓存键规则；忽略参数的节点仍可能命中，把参数纳入键的节点则可能产生不同对象。

CloudFront 缓存键文档可以帮助理解这个区别。判断冷热缓存，应该结合实际命中状态、源站日志与平台规则，而不是看到随机字符串就认定“绝对冷缓存”。同样，浏览器已经建立的连接可能继续复用，刷新页面不一定重现完全首次访问的条件。 如果业务主要依赖长期缓存的静态资源，刻意让每次请求都回源，可能测偏了目标；如果业务是不可缓存的动态接口，只测热缓存又会过度乐观。最有用的报告会分别描述两种场景，并说明哪一种接近日常业务。测试目的决定条件，不应倒过来为更好的成绩挑条件。

失败率要保留，成功样本也别只取最快一次

假设甲完成十次请求其中九次成功，乙十次全部成功，只比较成功样本的最快值就会隐藏重要差异。应先写出尝试次数、成功次数、失败类型，再讨论成功请求的耗时分布。用户主动取消也应与网络失败区分，因为取消不代表服务没有能力完成该请求。

本站对成功样本计算中位数，并单独记录失败与取消。中位数比挑最快一次更不容易被偶然值主导，但它不能替代完整分布，更不是稳定性保证。样本只有三次时，一个漂亮的中位数所代表的信息很有限；需要看尾部延迟或百分位时，应采用足够样本和清楚的方法，不能凭几次请求写出可靠的 P99 结论。 报告里保留异常样本，是为了让下一次排查有线索。某一轮显著变慢，可能是本地网络活动、源站响应、连接状态或缓存变化。记录时间与条件后再复测，比直接删除“离群值”更负责。只有在明确发现采集错误并说明处理规则时，才应调整样本集合。

一套适合小团队的测速顺序

先从真实业务目标出发，选两三个重要地区和主要网络，再选择能够代表请求特征的资源。每个候选使用相同版本、相同大小和相同类型的对象，记录证书、压缩、缓存规则与回源配置。在测试前确认内容能被正常读取，避免把配置故障混进线路比较。

随后做少量重复请求，保存原始结果；在不同时间段复测，并改变候选顺序，减少把时间变化误认为厂商差异的机会。如果测试期间设备在同步大文件、切换网络或运行其他任务，应标注这一条件。比较的是受控环境里的相对表现，不必把每一个波动都解释成网络架构结论。 最后回到真实页面，验证用户关心的动作。图片加载、页面可读、登录成功和文件下载完成，各自关注的体验不同。测速结果不错，而实际页面仍很慢时，需要继续检查资源体积、阻塞脚本、第三方请求和应用服务，而不是一遍遍换节点。本文的CDN 选型指南提供了把这些证据纳入采购的方法。

防护产品与免备案方案，测速应回答什么

评估高防CDN时，浏览器测速可以观察正常请求的交付体验，但无法证明攻击下的容量和保护效果。后者要依据具体方案、授权测试和厂商证据。把平时速度与防护能力分开记录，有助于避免“下载很快，所以一定扛得住攻击”这样的推断。

评估免备案CDN时，测试重点仍然是目标用户、访问时段和回源条件。产品接入条件与线路质量是不同问题，应该分别确认。某个地区一次成功并不能代表所有网络长期稳定，某个时段表现较差也需要进一步确定是源站、边缘还是本地条件导致。 不同平台的官方测速示例，也可能使用不同文件和测量方式。引用外部成绩时，应同时保留来源、时间与条件；无法获取这些信息，就不要将其混入自己的统一排名。对供应商资料的解释，可参阅防护服务比较方法。

如何写出一份不会误导下一位读者的结果

结果页至少写清六件事：测试何时发生、在哪里进行、网络是什么、请求哪份文件、采用什么缓存条件、样本如何统计。再附上失败数、原始数据和已知限制。如果想给出选择建议，应把建议约束在已验证的业务范围内，例如“这组条件下读取更稳定”，不要跳成“全球最快”。

“为什么上午与晚上结果不同？”先核对网络负载、对象状态、连接和源站，差异本身就是需要解释的观察。“为什么命令行可以而网页失败？”除了请求条件不同，还应检查浏览器跨域限制。“为什么速度超过了理解中的带宽？”先确认是否使用解码字节、是否有缓存以及时间统计口径。 测速的价值，是帮助下一步做决定：调整缓存、改变资源、检查回源，或者淘汰无法满足关键地区需求的方案。当报告能让另一位同事按同样条件复测，并理解数字为何变化，数据才真正从一张成绩单变成了工程证据。
