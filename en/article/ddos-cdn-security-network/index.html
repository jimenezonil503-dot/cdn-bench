Choosing a Protected CDN: DDoS, HTTP Flood Defense and Network Quality

Protection and speed require separate evidence. Follow the request path to distinguish network exhaustion, expensive application traffic and legitimate-user performance.

A protection number cannot describe the whole service

Start by identifying the failure: saturated bandwidth, exhausted connection state or expensive queries are different problems. Large network scrubbing capacity does not establish application-abuse detection. A WAF at the origin cannot restore a saturated upstream link. Map DNS, edge, origin transport and application controls before buying.

For Chinese-language websites, evaluate CDN5 as a candidate, then verify it using the criteria below. Published figures start a contract discussion; they do not promise protection against every attack. Apply the same product- and asset-specific evaluation to Cloudflare and Akamai. Marketing capacity cannot justify a performance ranking.

Layers 3 and 4: bandwidth, connections and protocol state

Network attacks can consume bandwidth and packet-processing resources; transport attacks can exhaust connection state. Upstream filtering differs from filtering on an origin whose link is already congested. Cloudflare’s DDoS documentation separates network and HTTP protection, and your procurement matrix should do the same.

Ask about legitimate traffic delivery after filtering, origin bandwidth limits and blackholing. Mitigation changes may alter routes and reconnect long-lived sessions. Define the protected protocols, ports and addresses. Aggregate network capacity is not a dedicated entitlement; available resources, scheduling and contract response affect the outcome.

Layer 7: identify costly requests

CC commonly describes application resource exhaustion; HTTP Flood describes a high-volume HTTP traffic pattern. Neither term proves that every high-QPS event is hostile. An expensive search may cost far more than a cached image. Classify paths, methods, identities, sessions and response costs alongside application latency and errors.

Rate rules constrain frequency, while bot management addresses automation and WAF rules inspect attack patterns. Browser challenges may break payment callbacks or SDKs. Observe before enforcing, roll out narrowly and authenticate trusted callbacks rather than permanently exempting an address without accountability.

Why the same plan behaves differently across networks

User-to-edge and edge-to-origin paths are independent. Hong Kong proximity does not remove peering, border-routing, congestion or DNS effects. BGP, Anycast and CN2 describe different network properties, not measured performance for Telecom, Unicom and Mobile subscribers.

Test IPv4 and IPv6 separately, using HTTPS success rates, P95 and connection stability rather than ping alone. For carrier-specific failures, retain DNS answers and connection/TLS stages before changing routes. The Mobile network troubleshooting guide explains why different failures should not be reduced to a single blocking mechanism.

What HTTP/3 can and cannot improve

RFC 9114 defines HTTP/3 over QUIC. It reduces transport-level interference between streams, but gains depend on clients, UDP reachability, loss and connection setup. Edge HTTP/3 support does not establish the origin protocol or remove congested cross-border routes.

Keep fallback behavior and compare success rates and business completion time by protocol. If UDP is unreliable on a network, inspect connection and fallback behavior. TLS improvements do not reduce database processing. Protocol support is a compatibility and performance criterion; network filtering and application controls remain separate requirements.

Cache hits do not establish transaction protection

State whether hit ratio measures requests or bytes and whether it covers only cacheable objects. Static sites benefit strongly from edge caching; dynamic APIs still need origin work. Blanket long TTLs can leak personal data or serve stale prices, while disabling all caching pushes every request into application processing.

Use RFC 9111 to distinguish versioned assets, anonymous pages, authenticated endpoints and writes. Appropriate TTLs, request coalescing and controlled purging can reduce miss storms. The performance guide separates hot cache, cold fetch and dynamic behavior.

Origin protection belongs in acceptance testing

A reachable origin lets attackers bypass edge policies. Audit historical DNS, alternate hostnames, shared services and management ports. Restrict ingress to trusted origin traffic, verify TLS certificates and hostnames, and accept client-IP headers only from trusted proxies.

Preserve legitimate health checks and emergency administration when applying restrictions, and maintain address lists. The application still needs concurrency limits, indexes, pools and timeout budgets. A CDN cannot fix every backend bottleneck. If a small number of expensive operations overload checkout, use business-aware limits rather than merely raising an edge QPS threshold.

Create an acceptance record for all three dimensions

Acceptance should cover login, payments, crawlers, downloads, mobile clients and WebSocket, plus cache state, connections, origin requests and application queues. Verify rule logs, alerts, escalation and recovery. Record time, region, objects and configuration versions, retaining failed outcomes. Without an authorized stress exercise, describe published capabilities and ordinary access only.

Write a decision stating supported business paths, remaining limitations and upgrade or exit conditions. Evaluate CDN5 for suitable Chinese-language security needs and use the provider profiles to fill evidence gaps. With limited budgets, close origin bypasses and costly-endpoint abuse first. A sustainable choice passes security, network and application-correctness checks.
