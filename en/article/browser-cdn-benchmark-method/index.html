Measurement and diagnosis

How to benchmark a CDN: response time, download rate, and failure evidence

Understand what a browser benchmark measures, how caching and compression affect results, and how to design a repeatable comparison without confusing throughput with bandwidth.

A browser benchmark answers a local question

A result depends on the time, device, network, object, compression, cache state, and connection behavior. Record those conditions beside the number. A browser test can expose repeated failures or stable differences in a particular environment, but a few requests cannot establish global superiority or attack resilience.

This guide follows the site's actual implementation. Numerical examples explain arithmetic rather than report provider performance. Read the measurement notes for the scope of the tool, and decide which operational question the experiment should answer before running it.

Distinguish response availability from body completion

The Fetch documentation explains that a response can become available before its body has finished arriving. Timing only the promise therefore does not measure a complete download.

This tool records elapsed time to the response object and elapsed time until the full body is read. The first can include scheduling, connections, network travel, and server work; it is not ICMP Ping or isolated origin processing. Comparing both timings helps identify whether waiting or subsequent transfer deserves investigation.

Effective rate is not line capacity

The tool multiplies bytes read by eight and divides by complete request time to report Mbps. Waiting time is included. An illustrative one-million-byte response completed in one second produces roughly eight Mbps under this definition. Compression can make decoded bytes differ from bytes transferred on the network.

PerformanceResourceTiming distinguishes transfer size, encoded body size, and decoded body size. Report the byte definition explicitly. Two charts labeled Mbps may be incomparable if their timing and size denominators differ. Neither automatically measures the subscriber's broadband capacity.

A CORS failure is not proof of a CDN outage

A resource that opens directly may still be unreadable to another site's script. A server can return a response that the browser withholds under CORS. The failed read establishes that the test did not complete, not that a particular node is unavailable.

MDN's CORS guide explains the limited error detail available to scripts. Inspect browser diagnostics and server evidence. This tool omits credentials; use authorized public resources without private tokens or personal data. See the configuration guide before changing response permissions.

Cross-origin timing has its own permission boundary

Successful body access does not expose every network timing field. Resource Timing documents restrictions and Timing-Allow-Origin, which serves a different purpose from Access-Control-Allow-Origin. A readable response can still lack detailed DNS, connection, or TLS measurements.

Do not replace unavailable fields with claims of zero latency or invent stages the tool did not collect. Start with reliable completion times and success counts, then add detailed instrumentation when needed. A smaller set of explainable measurements is more useful than an impressive but unsupported dashboard.

Confirm that the objects really match

Fix content version, size, type, and compression conditions. Similar filenames do not prove equivalent responses: one may be compressed, another redirected, and another an HTML error. Inspect the actual object and use a content check when appropriate.

Public library endpoints are convenient examples, not interchangeable substitutes for self-managed CDN deployments. For procurement, deploy authorized matching files behind each candidate. Choose sizes that represent the workload without imposing unnecessary transfer costs. Small objects emphasize waiting; larger objects reveal more of the transfer phase.

Separate cold cache, warm cache, and random queries

The tool adds a random query value and requests no browser HTTP-cache reuse to reduce some local interference. That does not guarantee a CDN miss. Whether query strings distinguish objects depends on the effective cache key, and existing connections may still be reused.

The CloudFront cache-key documentation illustrates the distinction. Confirm hit state using actual platform behavior and logs. Forced misses can misrepresent a static workload, while warm-cache-only results can misrepresent dynamic requests. Let the business question determine the test conditions.

Keep failures and avoid fastest-run selection

List attempts, successes, and failure types before comparing successful timings. User cancellation should be distinguished from network failure. A candidate with one very fast response and repeated failures should not win simply because the report selects its best run.

This tool reports medians for successful samples and records failures and cancellations. A median is not a guarantee, and a few samples cannot support a reliable tail-percentile claim. Preserve unusual results with their context and investigate before excluding them. Document any justified data-cleaning rule.

Use a practical, repeatable sequence

Choose important regions and networks, prepare equivalent objects, and record certificates, compression, cache policy, and origin configuration. Confirm that every object is readable before comparing delivery. Run limited repetitions and save raw results.

Repeat in other time windows, vary candidate order, and note local network changes or competing transfers. Then verify actual user journeys, since page readability and successful sign-in matter beyond file downloads. The CDN selection guide shows how to include these findings in a purchasing decision.

Keep delivery measurements separate from product promises

When evaluating a high-defense CDN, local downloads describe normal delivery, not attack capacity. That requires a defined plan, supporting evidence, and authorized validation. A fast file read is not proof that the application will remain healthy under abuse.

For offshore CDN onboarding, test relevant users, periods, and origin paths while confirming eligibility separately. External benchmark charts may use different objects and methods. Retain their sources and conditions rather than merging them into a misleading common ranking; see the protection comparison.

Make the result useful to the next reader

A report should name when and where testing occurred, the network, object, cache conditions, and aggregation method. Add failures, raw observations, and limitations. Constrain recommendations to the environment that was actually verified.

Morning and evening differences need context; command-line success with browser failure calls for checking request conditions and CORS; surprising throughput calls for examining bytes and timing. The goal is a decision about caching, resources, origins, or candidate suitability that another colleague can reproduce and challenge.
