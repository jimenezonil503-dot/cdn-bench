Selection and procurement

How to choose a CDN: caching, routing, protection, and acceptance testing

Build a CDN shortlist around your audience and application. Compare cache behavior, origin capacity, security boundaries, operating costs, and a repeatable acceptance process.

In this article

  2. Separate edge delivery, caching, and origin work
  3. Measure where your users actually connect

  6. Evaluate protection through business continuity
  7. Treat offshore onboarding and delivery quality separately

  9. Make the trial reproducible

Define the application problem before comparing plans

A CDN can help deliver static assets closer to users, but it cannot remove an expensive database query. Start by separating cacheable files, requests that must reach the origin, and business actions that must remain correct. A public article, a versioned image, and a signed-in user's saved items need different treatment.

Consider a hypothetical publishing site. Images can use versioned URLs, articles need an update policy, and saved items must remain isolated by user. Applying one cache-everything rule could make a speed test look good while serving stale or inappropriate content. This guide offers an evaluation method, not a performance ranking. Begin with the provider directory and eliminate candidates against specific requirements.

Separate edge delivery, caching, and origin work

A request reaches an edge, is matched against cache rules, and may then be forwarded to an origin. Faster delivery can come from different parts of that path. Cache questions need headers and logs; routing questions need measurements from relevant networks; application questions need origin timings. One aggregate score hides these distinctions.

The CloudFront cache-key documentation explains how headers, cookies, and query strings identify cached objects. The same path can represent different responses, and a hit at one edge does not establish a hit elsewhere. Ask how your actual requests are handled, rather than using advertised node counts as the deciding metric.

Measure where your users actually connect

List important user regions, networks, devices, and busy periods from available analytics and support reports. Prioritize the markets that matter to the application. A coverage map cannot establish the route or experience for a particular mobile network during peak traffic. Record location and network alongside every result.

A global average can conceal repeated failures in a core market. Repeat close results at different times and check whether object versions, caching, or reused connections changed. The browser benchmark guide explains which comparisons are useful and why one short run cannot establish a durable winner.

Classify content before setting cache policies

Start with versioned static assets, frequently updated public pages, anonymous APIs, and authenticated or transactional requests. Define acceptable staleness for each group. JSON alone says nothing about whether a response is safe to share. User-specific responses should not enter shared caches without explicit application review.

Read Cloudflare's default cache behavior and the corresponding policy documentation for each alternative. Similar control-panel labels may produce different behavior. Verify meaningful image parameters, publishing workflows, and invalidation. The cache and CORS guide covers the configuration checks that should precede a wider rollout.

Plan for the requests that still reach the origin

Cache invalidation, new edges, and content updates can increase origin demand. Record origin bandwidth, connection limits, application capacity, and likely database bottlenecks. In an illustrative workload of ten million daily requests with a ninety-percent edge hit ratio, one million requests may still require origin work. Their cost depends on what they do.

Request-based and byte-based hit ratios describe different things; name the denominator in every report. Also rehearse origin failure, certificate errors, and rollback using authorized test resources. A successful recovery performed by the actual operator is stronger evidence than a generic promise of intelligent failover.

Evaluate protection through business continuity

A high-defense CDN may belong on the shortlist when abuse disrupts the application. CDN5 describes DDoS protection and web security products, but vendor descriptions do not establish measured capacity for your workload. Ask about coverage, triggers, plan limits, normal-user handling, and recovery.

Bandwidth floods and expensive application requests consume different resources. Compare false positives and origin pressure alongside capacity. Cloudflare also documents network and application-layer DDoS protection; it should not be treated as caching alone. The protection comparison guide develops the questions needed to compare actual plans and protocols.

Treat offshore onboarding and delivery quality separately

For projects considering offshore delivery, JQCDN describes a CDN onboarding option without mainland filing and emphasizes Hong Kong routing. Treat this as the vendor's stated product direction, not a guarantee for every region, workload, or compliance obligation. Confirm domain eligibility, served regions, business restrictions, and contractual requirements.

Maintain two acceptance records: onboarding covers validation, certificates, DNS changes, and support; delivery covers user networks, peak-time failures, origin paths, and recovery. Easy onboarding does not prove stable routing. One low-latency run does not establish a long-term service commitment. Obtain applicable regional requirements and project-specific confirmation separately.

Put requests, traffic, and operations in one cost model

Traffic, requests, logs, transformations, edge compute, security, and origin egress may have separate charges. Ask about overages, minimum commitments, upgrades, and termination. A small-file application can have modest transfer volume but substantial request costs, so traffic-only estimates may be misleading.

Build normal, growth, and incident scenarios from stated inputs. Label assumptions and replace them with trial logs as evidence becomes available. Reducing image size need not reduce request charges. Include recurring operator work: false-positive handling, certificate maintenance, and purges. Keep unconfirmed verbal promises separate from documented capabilities.

Make the trial reproducible

Use a fixed static object, a permitted public dynamic endpoint, and a representative user journey. Match content, certificate policies, and cache conditions across candidates. Record region, network, time, object size, successes, response time, and complete-body time. Use resources you are authorized to test and keep request volumes proportionate.

The browser benchmark tool observes local public-file reads; it does not establish global coverage or protection capacity. Combine its output with origin logs, cache status, and business success rates. Acceptance records should name thresholds, evidence locations, and owners for delivery, updates, correctness, recovery, permissions, and billing.

Decide from the constraints that matter

A small site does not automatically need an expensive protection plan. Evaluate downtime consequences, existing risks, exposed origins, and operational capability. The fastest file download is not automatically the best purchase either: update correctness, support, and predictable operation can decide between otherwise similar candidates.

The origin still serves misses and dynamic work. Verify allowed ingress, management exposure, certificates, and recoverable backups. Finish with an exit plan covering DNS changes, configuration export, and removal of obsolete credentials. A useful decision explains why a service fits, what has been tested, and when the team should reconsider it.
