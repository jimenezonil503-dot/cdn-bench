Caching and cross-origin requests

CDN caching and CORS: response headers, stale content, and release checks

Troubleshoot stale content and cross-origin failures by separating browser caches, edge policies, cache keys, credentials, preflights, and application correctness.

Start with the actual response

After CDN onboarding, a directly accessible file may become unreadable to a page script, published content may stay stale, or signed-in behavior may change. These involve different mechanisms. Inspect the request and response, locate the relevant cache layer, then check origin permissions and identity handling.

Status, content type, Cache-Control, Age, Vary, and vendor-specific cache information help establish what happened, but no single header explains the whole path. This guide uses a hypothetical mix of public pages, versioned files, and private APIs. For purchasing decisions, start with the CDN selection guide.

Separate browser, edge, and origin state

Browser caches serve local reuse; edge caches can share responses among visitors; origins generate or store the source content. Purging an edge does not necessarily invalidate an already cached browser copy. Clearing one browser does not change other visitors' state.

Versioned asset URLs can make releases more predictable: publish a new URL when content changes and retain old files for older pages. Public pages and private APIs need different freshness requirements. Define acceptable staleness before choosing TTL and invalidation behavior.

Understand no-cache, no-store, and shared-cache controls

MDN's Cache-Control reference distinguishes storage from reuse. No-cache requires validation before reuse; no-store directs caches not to store the response. Request directives and response directives must also be distinguished.

Private limits shared caching rather than providing authentication. Public must not be applied casually to personalized data. Max-age and s-maxage have different scopes. Compare origin headers with the actual edge response and effective rules, since custom platform settings can change default handling.

Derive the cache key from response variation

The same path can produce different languages, sizes, identities, or signed content. Failing to distinguish meaningful inputs risks serving the wrong object; including every irrelevant value fragments the cache. Start from which inputs genuinely change the response.

The CloudFront cache-policy documentation explains headers, cookies, and queries. Image dimensions may need separation; analytics parameters may not, depending on application behavior. Signed access requires verifying authorization on cache hits too. A high hit ratio is not a success when it bypasses business conditions.

Draw the boundary around user-specific responses

Profiles, orders, balances, and administration should not be shared merely because paths match. Test at least two identities and an anonymous visitor. One account repeatedly refreshing cannot reveal every isolation error.

Set-Cookie and authorization handling depend on platform rules and configuration. Read Cloudflare's default behavior where relevant, then verify the deployed policy. For uncertain endpoints, begin without shared caching and approve narrowly defined exceptions through application review.

CORS governs browser reads, not application authorization

MDN's CORS guide describes how browsers expose cross-origin responses. Origins include scheme, host, and port. A direct browser navigation or command-line success does not establish that a different website's script can read the response.

Some requests may already have reached the server before the browser withholds access to the response. Authentication, authorization, and CSRF protection still need independent design. Choose permission scopes around whether a resource is public and whether credentials, custom headers, or particular methods are involved.

Credentialed reads need explicit origin handling

Credentialed cross-origin access cannot use a wildcard allowed origin in place of a specific permitted origin. Client credential mode, cookie properties, and other browser rules also matter. One correct response field does not establish the entire request path.

Do not reflect arbitrary Origin values as a shortcut. Validate against intended callers and test allowed, disallowed, and same-origin cases. Repeat after a cache hit to ensure a previously generated permission is not incorrectly reused for another origin. Sensitive response access deserves application-level review.

Match dynamic origin permissions to cache variants

When Access-Control-Allow-Origin varies by request origin, consider how those variants are cached. MDN documents Vary: Origin, but platform support and cache-key configuration must still be checked rather than assumed.

Request from two allowed origins and then a disallowed one, observing cached responses as well as misses. If content also depends on identity, origin variation alone cannot provide isolation. Decide which error responses may be exposed and return consistent, intentional permissions without leaking sensitive diagnostics.

Treat preflights as a separate request stage

Some requests first use OPTIONS to check permitted methods and headers. The trigger depends on the full request conditions, not merely GET versus POST. A failed preflight and an unreadable response after a sent request are different failure paths.

Check gateway, authentication, redirect, and protection behavior for OPTIONS. Verify both preflight and actual-response permissions. Preflight caching is distinct from edge object TTL. When a change appears ineffective, identify the retained state before modifying several layers at once.

Trace stale content from deployment outward

First confirm that the origin serves the expected version and that page references match the deployed assets. Then inspect the relevant edge object, purge scope, query variants, and browser reuse. Application caches and intermediary layers can add further state.

Avoid whole-cache purges as the routine first response: they can increase origin pressure and hide the cause. Prefer scoped invalidation where possible, retain old release resources, and keep a rollback plan. Also check whether older clients or outdated API references are simply requesting different content.

Revalidate configuration when switching delivery products

After moving to a high-defense CDN, check whether rules affect APIs, preflights, or legitimate machine callers. A protection page cannot be repaired merely by adding a cross-origin header; inspect the event and expected response first.

An offshore CDN option does not change HTTP cache semantics or browser permission boundaries. Recheck regions, origin paths, and rule behavior during migration. The service comparison guide explains why real responses and documented unknowns matter more than similarly named switches.

Finish with business-level acceptance

Exercise anonymous and authenticated users, different roles, allowed and disallowed origins, resource updates, and reversible error cases within an authorized environment. Preserve requests and timestamps. Verify monitoring for wrong content types, unusual status codes, cache changes, and origin demand.

Save final configuration and rollback instructions, removing temporary allowances used during debugging. The benchmark tool and measurement guide can then help inspect delivery. Speed becomes useful only after the object, user, permissions, and update behavior are correct.
