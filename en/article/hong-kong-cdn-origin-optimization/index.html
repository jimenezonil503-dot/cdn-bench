Hong Kong CDN Performance: Mainland Latency and Origin Optimization

Decompose TTFB, cache state and origin work to identify what Hong Kong delivery improves, then optimize keys, connections and publication.

CDN Bench editorial · 2026-10-14 · Updated 2026-10-147 min read
In this article
  1. Start with whether a request reaches the origin
  2. TTFB is not a transit-only measurement
  3. Find the most valuable cacheable objects
  4. Prove response equivalence before simplifying keys
  5. Optimize origin connection and queuing
  6. Headers start diagnosis; logs supply context
  7. Validate improvements with comparable samples

Start with whether a request reaches the origin

Cached public objects can reduce distance, while misses and dynamic operations still reach origins and databases. Hong Kong proximity alone does not guarantee improvements across carriers or times.

CDN5 is a possible pilot candidate, not a measured winner here. Product information was checked on 14 October 2026. Establish the carrier baseline before changing settings.

TTFB is not a transit-only measurement

Timing definitions vary; retain DNS, transport, TLS, request wait and download stages. Slow queries, challenges, misses and new connections can all raise TTFB.

Separate reused/cold connections, cache states and protocols. QUIC and HTTP/3 change transport behavior without eliminating distance or guaranteeing universal gains. Validate support and fallback.

Find the most valuable cacheable objects

Prioritize size, frequency and origin cost. Small-image hits can hide large-file misses, while rare costly APIs dominate database work. Inspect request hits, byte hits and origin work together.

Prove response equivalence before simplifying keys

RFC 9111 requires correct freshness and response semantics. Exclude tracking dimensions only after proving they do not affect content or authorization; identical status codes are insufficient.

CloudFront cache-key guidance clarifies headers, cookies and queries. Key inclusion and origin forwarding are separate questions. Test identity isolation and plan invalidation when policies change.

Optimize origin connection and queuing

Inspect connection reuse, timeouts, origin certificates and Host. Very short timeouts can trigger retries; long ones can accumulate queues. Correlate load-balancer, application, database and external-dependency timing before relocating origins.

For shield caches, measure fetch reduction and failure behavior. Control refill concurrency, stage releases and warm only selected objects. Publish new assets before pages referencing them.

Headers start diagnosis; logs supply context

Retain Cache-Control, Age, Vary, ETag and provider cache-status fields, but account for multiple layers and revalidation. Correlate browser responses with edge and origin logs rather than inferring the entire chain from one header.

Use versioned, removable test resources and expected content checks. Do not permanently expose sensitive diagnostics or leave cache-bypass parameters and excessive logging behind.

Validate improvements with comparable samples

Change few variables at a time and hold resources, application version and audience groups stable. Track P50, P95, errors, cache state and content. Audience/device mix changes can distort real-user comparisons.

Document rules and rollback, then monitor new pages, parameters and authentication behavior. Use path analysis for unexplained carrier problems. Better task completion and controlled origin work matter alongside speed.

If averages improve but failures worsen, pause expansion. Include weaker devices, mobile access and cold caches, and ensure rollback will not trigger an uncontrolled refill.
