HTTP Flood Defense: Identification, WAF Rules and CDN Controls

Distinguish HTTP floods, campaigns and application faults using request evidence, then design WAF matching, counters, actions and feedback.

CDN Bench editorial · 2026-10-14 · Updated 2026-10-147 min read
In this article
  1. High traffic alone does not establish an HTTP flood
  2. Trace requests into resource consumption
  3. Separate matching, counting and action
  4. Respond to behavior, not one signature
  5. Cache-bypass controls need content semantics
  6. Bot controls and challenges have limits
  7. Origins still need work limits
  8. Demonstrate improvement rather than coincidence

High traffic alone does not establish an HTTP flood

High QPS can come from campaigns, crawlers or retries as well as HTTP floods. Correlate distribution, completion, cache and origin work; popularity alone is a poor detector.

This defensive guide uses documentation checked on 14 October 2026. During outages follow CC incident response; lasting policies need explainable work-budget evidence.

Trace requests into resource consumption

Correlate normalized routes, methods, identity classes, cache and edge actions with origin timing, queues and databases. Redact secrets and document sampling.

High errors may indicate abuse or a broken client; long execution may reflect costly inputs or database changes. Validate hypotheses rather than relying on address counts or browser labels.

Separate matching, counting and action

Use rate-rule documentation to verify tier-specific fields. Define route/method scope, trustworthy counters and then suitable action.

Handle shared egress with meaningful identities and aggregate budgets. Distinguish observation from enforcement and document ownership and rollback for overlapping policies.

Check evaluation order and exceptions: earlier decisions can bypass later controls. Verify actual platform semantics with bounded samples rather than inspecting one rule in isolation.

Respond to behavior, not one signature

These are diagnostic directions, not universal signatures. Legitimate clients can show similar behavior, so validate before enforcing.

Cache-bypass controls need content semantics

Apply RFC 9111: cache stable public responses without sharing identity-bound work. Inspect meaningful headers, cookies and parameters before simplifying keys.

Bound purges/warming and inspect cached errors. Cloudflare cache documentation helps map product behavior; high overall hits can hide costly dynamic routes.

Bot controls and challenges have limits

Bot documentation describes additional capabilities requiring tier/log verification. Do not invent accuracy rates. Legitimate automation and accessibility clients need appropriate treatment.

Interactive challenges may break APIs and callbacks. Use authenticated quotas and signatures, tracking legitimate failures and task completion. The goal is controlling unauthorized or excessive work, not all automation.

Origins still need work limits

Close bypasses and enforce application validation, timeouts, pools and concurrency. An allowed request must still have bounded work; rejected writes need safe retries and idempotency.

Evaluate CDN5 where relevant for controls, logs and support without treating a bundle as application governance. See lasting CC protection.

Demonstrate improvement rather than coincidence

Compare legitimate completion, origin resources, errors and tails while accounting for traffic changes. Preserve controlled changes and negative results; do not credit natural attack cessation entirely to a policy.

Review rules with releases, remove expired exceptions and reuse redacted regression samples. Maintain explainable, reversible decisions.
